# Alpaca notes

Verified findings for `semis_paper_trading_brief.md`'s working rule 2 ("verify every
Alpaca-specific behavior against the official documentation before relying on it"). Each
entry below was checked against Alpaca's docs during Phase 0 (2026-09-17/18); dates matter

## Endpoint and SDK

- Paper base URL: `https://paper-api.alpaca.markets`.
  Source: <https://docs.alpaca.markets/us/docs/paper-trading.md>
- `alpaca-py`'s `TradingClient` takes `paper=True` to talk to the paper environment; keys
  must be a paper account's own keys, not a live account's.
  Source: <https://alpaca.markets/sdks/python/trading.html>,
  <https://alpaca.markets/sdks/python/api_reference/trading/trading-client.html>

## Fill simulation

- Orders are matched against real-time NBBO quotes and fill "only when they become
  marketable."
- Not modeled at all: market impact, information leakage, latency slippage, queue
  position, price improvement, regulatory fees, dividends, borrow fees.
- Order size is **not** checked against quoted size -- "you can submit and receive a fill
  for an order that is much larger than the actual available liquidity."
- Partial fills: "eligible orders receive partial fills for a random size 10% of the
  time." The remaining quantity is re-evaluated for a later fill if still marketable.

  All of the above confirms the brief's own "Alpaca facts to confirm" section verbatim.
  Source: <https://docs.alpaca.markets/us/docs/paper-trading.md>

## Order types, time-in-force, and GTC expiry

- Order types: market, limit, stop, stop-limit, plus bracket / OCO / OTO / trailing-stop
  as advanced types.
- Time-in-force: `day` (regular hours, auto-cancels unfilled at the close), `gtc`
  (**auto-canceled after 90 days** -- Alpaca's "aged order policy"), `opg`/`cls`
  (auction-only, rejected if submitted 9:28am-7:00pm ET / 3:50pm-7:00pm ET respectively),
  `ioc`, `fok`.
- Limit/stop price precision: 2 decimals at or above $1.00, 4 decimals below $1.00.
  Source: <https://docs.alpaca.markets/us/docs/orders-at-alpaca.md>

## Wash-trade rejection

- Alpaca checks every incoming order for a potential wash trade against currently open
  orders in the same symbol and rejects it (HTTP 403) if the two could interact -- e.g. a
  resting buy limit and an incoming sell limit that could match.
- Bracket, OCO, and trailing-stop orders are exempted from this check (they're
  Alpaca-recommended for take-profit/stop-loss situations specifically because of this).
  **Confirmed with a direct quote (S4 Phase 3, 2026-09-21)** from
  <https://docs.alpaca.markets/us/docs/user-protection>: *"If a customer wants to set up a
  'take profit' and a 'stop loss' situation, we recommend using a bracket or OCO...order.
  These complex orders and trailing stop orders are exceptions to our wash trade
  protection."* This quote names bracket/OCO/trailing-stop specifically, not OTO --
  `intraday/orders.py::build_entry_order`'s stop-only leg uses `OrderClass.OTO`, so its
  wash-trade exemption is **not** confirmed by this quote and remains a "still to verify"
  item below.

## `client_order_id`

- String, **maximum 128 characters**. Auto-generated by Alpaca if omitted. No other format
  constraint documented (a UUID is Alpaca's own example, not a requirement).
  Source: <https://docs.alpaca.markets/us/reference/postorder.md>

  This is the number `execution/orders.py` (Phase 3) needs when building the deterministic
  id from sleeve + strategy version + rebalance date + symbol + attempt number.

## Fractional and notional orders

- Supported for market, limit, stop, and stop-limit orders, **`time_in_force=day` only**.
- `qty` and `notional` are mutually exclusive -- setting one nulls the other.
- **No fractional short sales** -- "all fractional sell orders are marked long."
- Requires the asset's `fractionable` flag; a non-fractionable symbol rejects with
  "requested asset is not fractionable."
- **`qty` precision: up to 9 decimal places.** Found while auditing for more instances of
  the same defect class as the `limit_price` sub-penny rejection (2026-09-23,
  `execution/orders.py::round_to_tick`): `build_orders`'s own `qty = abs(delta_notional) /
  price` is a raw float division with no rounding at all for a fractionable symbol (only
  non-fractionable symbols get `math.floor`'d), so it can produce far more than 9 decimal
  digits (`5000.0 / 190.0 == 26.31578947368421`, 14 places) -- never yet triggered in
  production because s3 (the only `trading_enabled` sleeve) hadn't reached its first
  monthly rebalance since go-live, so `run_execute` had never actually submitted a real
  order to hit this. Fixed by rounding to 6 decimal places, comfortably inside the limit
  with no measurable effect on the traded notional.
  Source: <https://docs.alpaca.markets/us/docs/fractional-trading.md>

## Market data plans

- The Basic (free) plan gives real-time data from **IEX only**, not the full consolidated
  tape.
- Consolidated (SIP) data is available on the Basic plan **delayed by 15 minutes**
  ("real time IEX or 15 mins delayed SIP").
  Source: <https://docs.alpaca.markets/us/docs/about-market-data-api.md>

  Confirms the brief's assumption. **Not yet verified**: the exact API call shape for
  pulling 15-min-delayed SIP minute bars for the after-the-fact cost analysis T5
  mentions -- to be checked in Phase 6 against the real account's actual plan.

- **S4 calls added 2026-09-30, both `feed=DataFeed.IEX`** (`execution/market_data.py`):
  `get_stock_latest_trade(StockLatestTradeRequest(symbol_or_symbols=[...]))` for the
  pre-market fallback (`AlpacaMarketDataClient.latest_trades`), and
  `get_stock_bars(StockBarsRequest(..., timeframe=TimeFrame(5, TimeFrameUnit.Minute),
  adjustment=Adjustment.SPLIT))` for the Trader's `session` section
  (`AlpacaMarketDataClient.bars`, about two weeks of 5-minute bars per cycle for the
  symbols in view). Signatures checked against the installed alpaca-py 0.44.0; **not yet
  verified against the real account**. The first research and cycle runs on 2026-10-01
  are the test: the research `info` incident (`premarket moves: N/14 tickers priced`) and
  a non-empty `session` section in the Trader's context, or a `session bars unavailable`
  warning saying why not. Why IEX: the free plan's SIP data is 15 minutes delayed, too
  stale for an intraday trigger. IEX volume is a small slice of the tape, so relative
  volume compares IEX only with IEX (`intraday/session.py`).

- **S4 spread gate on the delayed consolidated quote, added 2026-10-01**
  (`AlpacaMarketDataClient.latest_quotes`): `get_stock_latest_quote(
  StockLatestQuoteRequest(symbol_or_symbols=[...], feed=DataFeed.DELAYED_SIP))`, set by
  `intraday.risk.spread_feed`. Why: IEX is one exchange with a thin book in these names.
  On 2026-10-01 its quote put MU and AMD 75-470 bps wide at nearly every cycle, failing
  the 50 bps gate, while the consolidated spread for stocks this liquid is a few cents
  and Alpaca paper fills against the consolidated quote. A 15-minute-old consolidated
  spread still answers "is this name liquid". Prices now come from the latest IEX trade
  (an existing call), which can't print outside the consolidated quote, falling back to
  the IEX quote midpoint. **Not yet verified against the real account**: whether
  `delayed_sip` is accepted on the latest-quote endpoint on the free plan. If it isn't,
  every cycle logs a `delayed_sip quotes unavailable (...); spreads checked on the IEX
  quote` warning and behaves as before. With a paid plan, `spread_feed: sip` makes the
  check real-time. **Verified 2026-10-02**: the first session with it logged no such
  warning and no spread failures for MU, AMD or NVDA (Oct 1, on IEX: about 30).

- **Pre-market trades from the delayed consolidated tape, added 2026-10-03**
  (`intraday/jobs.py::_todays_trade_prices`): `get_stock_latest_trade(
  StockLatestTradeRequest(..., feed=DataFeed.DELAYED_SIP))` alongside the IEX call, the
  more recent of the two prints winning. IEX alone priced 3 and 2 of 14 tickers in the
  07:30 CT research runs of Oct 1 and Oct 2. **Not yet verified against the real
  account**; the research `info` incident now says how many tickers came "from delayed
  consolidated trade", and a failed delayed lookup just leaves those tickers to IEX.

**Phase 12b market-data surface** (`execution/market_data.py::AlpacaOptionsMarketDataClient`,
verified against the installed `alpaca-py` 0.44.0 models, not yet against a real account --
both gates above are still unresolved, so no options-capable request has actually been
sent):

- `OptionHistoricalDataClient.get_option_chain` (`OptionChainRequest`, filtered to an exact
  `strike_price_gte == strike_price_lte`/`expiration_date`/`type` so at most one contract
  matches) resolves a proposal's own `expiry`/`strike`/`right` straight to its quote --
  Alpaca generates the OCC symbol itself as the response dict's key; this project never
  constructs one. `OptionsSnapshot.latest_quote` gives bid/ask.
- Tries `feed=OptionsFeed.OPRA` first; on a 401/403 (this paper account not entitled) falls
  back to `feed=OptionsFeed.INDICATIVE`. Which one actually answered is recorded on every
  quote (`OptionMarketQuote.feed`) -- this *is* how Stage 4 answers its own "does the feed
  produce sane pricing" question, so it's part of the record, not just plumbing.
- **`OptionsSnapshot` has no open interest or daily volume field at all** (checked directly
  against `OptionsSnapshot.model_fields`: only `symbol`/`latest_trade`/`latest_quote`/
  `implied_volatility`/`greeks`). Open interest instead comes from `TradingClient.
  get_option_contract` (the *trading* API's own contract metadata, `open_interest: str |
  None`) -- used strictly read-only here, same `paper=True`-hardcoded client
  `AlpacaPaperBroker` already builds. Volume comes from `OptionHistoricalDataClient.
  get_option_bars`'s current-day bar; `0` if none has formed yet.
- `OptionsSnapshot.implied_volatility`/`.greeks` (feed-reported) are deliberately never
  read -- `intraday/options.py::price_contract` recomputes both from the quote's own
  bid/ask midpoint, the same "never trust a feed's reported IV" discipline `data/
  options.py`'s module docstring already established for the unrelated `--implied-vol`
  path.

## Official MCP server

- Package: `alpaca-mcp-server`. Defaults to paper trading (`ALPACA_PAPER_TRADE=true`);
  live trading requires explicitly setting it to `false` with live keys.
- Exposes ~65 tools, including order placement (`place_stock_order` etc. -- market, limit,
  stop, stop-limit, trailing stop, brackets), account/position/watchlist management, and
  market data.
- Claude Code configuration:
  ```
  claude mcp add alpaca --scope user --transport stdio uvx alpaca-mcp-server \
    --env ALPACA_API_KEY=your_alpaca_api_key \
    --env ALPACA_SECRET_KEY=your_alpaca_secret_key
  ```
  The server's own docs warn against pasting keys into chat, recommending the MCP client's
  `env` block or an OS secret store instead -- consistent with this project's own
  boundary ("Configure Alpaca's MCP server with anything other than sandbox keys" is a
  **Never**). This project does not configure the MCP server itself; the note is here in
  case that's ever wanted for interactive/manual account inspection.
  Source: <https://docs.alpaca.markets/us/docs/alpaca-mcp-server.md>

## `alpaca-py` 0.44.0 SDK internals

Phase 4, verified against the installed package's source and pydantic model fields, not
just documentation.

- **Numeric fields are strings on the wire.** `Position.qty`/`.market_value`/
  `.avg_entry_price`, `Order.qty`/`.filled_qty`/`.filled_avg_price`/`.limit_price`, and
  `TradeAccount.equity`/`.cash`/`.buying_power` are `str` or `Optional[str]`, never a plain
  `float`, on the pydantic models (`.model_fields`, checked directly).
  `execution/alpaca_broker.py` coerces every one.
- **`Order.status` has 18 values**: `new, partially_filled, filled, done_for_day, canceled,
  expired, replaced, pending_cancel, pending_replace, pending_review, accepted,
  pending_new, accepted_for_bidding, stopped, rejected, suspended, calculated, held` --
  far more than this project's 7-value `OrderStatus`. `_map_order_status` in
  `alpaca_broker.py` buckets them; see that module's docstring for the exact mapping and
  reasoning per status.
- **`Order.side`/`.type` are `Optional`** -- `None` for a multi-leg order (`order_class`
  other than `simple`: bracket/OCO/OTO), where side/type live per-leg instead.
- **`alpaca.common.exceptions.APIError`**: `.status_code` reads
  `http_error.response.status_code` (can be `None`); `.message`/`.code` parse
  `response.text` as JSON and can themselves raise `json.JSONDecodeError`/`KeyError` if
  the body isn't shaped as expected (a proxy error, an outage) -- any translation code
  must swallow that, never let it mask the original error.
- **The SDK retries `429`/`504` internally**: 3 attempts, 3 seconds apart
  (`alpaca.common.constants.DEFAULT_RETRY_ATTEMPTS/_WAIT_SECONDS/_EXCEPTION_CODES`), not
  configurable via `TradingClient`'s constructor. A `RateLimitError` from this project's
  code only ever surfaces after that's already exhausted.
- **`Calendar.open`/`.close` are naive, already-exchange-local `datetime`s** --
  `Calendar.__init__` does `datetime.strptime(date + " " + "09:30", "%Y-%m-%d %H:%M")`
  directly on the raw API string, confirmed by reading the source. No timezone
  conversion needed or wanted when extracting `.time()`.
- **Duplicate `client_order_id` is rejected, not idempotent.** Verified via WebFetch/
  WebSearch against Alpaca's docs and two independent community sources (a forum thread
  and Alpaca's own "How to Fix Common Trading API Errors" guide): a repeated
  `client_order_id` gets **HTTP 422, `"client_order_id must be unique"`** -- the opposite
  of what this project originally assumed (`execution/orders.py`'s docstring said "real
  Alpaca" treats it as idempotent; that was wrong and has been corrected).
  `AlpacaPaperBroker.submit_order` catches this specific rejection and falls back to
  `get_order_by_client_id`, restoring the intended retry-safety via a fallback lookup.
  **Confirmed against a real paper account (2026-09-18)**:
  `tests/test_alpaca_broker_integration.py::test_duplicate_client_order_id_falls_back_to_lookup`
  passes -- a second submit with the same `client_order_id` really does 422, and the
  fallback lookup really does resolve to the original order.
- **`cancel_order`'s status codes**: `DELETE /v2/orders/{id}` returns `404` if the order
  id doesn't exist, `204` on success. Sourced from Alpaca's GitHub-hosted docs and a
  corroborating summary. **Confirmed against a real paper account (2026-09-18) with one
  correction**: canceling an *already-canceled* order does **not** return 422 -- it
  succeeds silently (idempotent), unlike `FakeBroker`, which raises `ValueError` for the
  same case. `AlpacaPaperBroker.cancel_order` doesn't special-case this; see its module
  docstring. Whether canceling a *filled* or *expired* order still returns 422 remains
  unconfirmed -- only the already-canceled case has been observed directly.
- **Market-closed order submission is queued, not rejected.** Verified via WebSearch:
  Alpaca used to reject day-order submission while the market was closed; it now accepts
  the order and routes it at the next open. `execution/pretrade.py`'s market-open check
  remains the only real gate for this condition -- there is usually no server-side
  rejection for `AlpacaPaperBroker` to translate into `MarketClosedError`. **Not yet
  confirmed against a real account.**
